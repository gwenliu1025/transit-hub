# 日快照完整性与昨日统计修复

## 已证实根因

`LiveMetrics` 保存的是访问时的日内采样；原午夜任务只要发现该日已有快照便跳过，因此最后一次白天访问值被永久当成完整昨日。该条件早于 v0.1.16；本轮源码比较不支持把它归因为最近自然周/月修复。另有成本依赖跨日 TodayConsume 缓存、来源失败写零、缺昨日时前端拿前天比较的问题。

## 实现与消费者

- `backend/internal/modules/dashboard/metrics_service.go` 持有日结。计划时间为北京时间 00:05，避免刚过零点时来源落库尚未收敛；启动只补真实昨日营收，不用当前倍率追溯旧日成本。
- `metrics_repository.go` 是日内采样、日结及已验证营收回填的唯一写入口。收入和成本分别持有完整性，旧行及日内采样默认未完成；失败侧保留原值和完成性。迟到日内写入在数据库入口及冲突行锁后检查业务日期，不覆盖已结算值。历史余额原位保留，缺历史采样时保持未知。
- `upstream/daily_usage.go` 持有指定自然日消费协议适配。Sub2API 明确传入 Asia/Shanghai；New API 使用同一北京时间日界。缺实际金额、非法数值、认证或请求失败均不当零消费。四个 worker、90秒总预算和 HTTP 取消传播限制调用。
- 计划日结延续既有“本次冻结配置的站点实际消费 × 充值倍率”口径，不声称恢复全天逐笔费率。持久化站点集合核对运行缓存；配置、身份、集合变化及 ABA 均拒收。最终复核至 dashboard 唯一写入结束保持同一配置锁，避免采集后修改配置仍被标完整。
- 历史响应增加 `revenueComplete`、`purchaseComplete`、`balanceRecorded`。前端唯一投影 `dashboardMetrics.ts` 按对应标志消费；净利需要收入和成本都完整。精确匹配北京时间昨日，不拿更早日期顶替；统一日期轴以 null 表示缺口，周期缺日不展示伪总额，利润率对比与续航同步保持未知。

## 历史恢复边界

`ReconcileRevenue` 仅消费真实昨日，避免有日志保留期的统计接口把旧日空结果当零。`ApplyVerifiedRevenue` 是内部受控恢复入口，只接收调用方已经核对完整覆盖的历史营收，不查询旧日志、不补写成本或余额，也不开放新的 HTTP 写入口。

维护命令 `backend/cmd/reconcile-dashboard` 随正式镜像构建为 `/app/reconcile-dashboard`，通过 `--input` 消费具名用户/工作区和连续日期营收。默认只读 dry-run，不初始化 schema；正式执行必须同时传入 `--apply --expected-plan-sha256`。计划绑定输入及完整写前行，事务锁定工作区与全部既有目标行后核对，复用 `ApplyVerifiedRevenue` 写入，并在提交前后验证营收、成本/余额保全。2分钟总预算、5秒锁等待；缺行、漂移或不合法输入拒收，提交未知与提交后回读失败分别报告，不自动重试。持续事务/锁/回滚回归由同目录测试持有。

历史营收可以使用站点既有长期聚合，但必须逐日核对覆盖、小时桶、水位以及仍完整保留的原始日志。历史成本需要该日真实消费、当时站点身份和充值倍率依据；现存分组倍率历史不等于充值倍率历史。证据缺失时保留旧数值和未完成标志，不按当前配置推算旧账。

- 两项第一轮检查反例（缓存缺成员、采集到落库间隙）已由原 writer 修复并补回归；最终完整来源全量验证和独立Fresh Check均成立。
