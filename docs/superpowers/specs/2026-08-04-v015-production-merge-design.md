# TransitHub v0.1.15 生产修复合并与公开发布设计

## 目标

以官方 `deviseo/transit-hub` 最新 `main` 为代码基线，保留其 `v0.1.15` 完整功能；将当前生产环境已经验证过的修复按新版本结构重新移植，形成可测试、可构建、可追溯、可公开分享的 `gwenliu1025/transit-hub`。

## 基线与远程关系

- `upstream`：`https://github.com/deviseo/transit-hub.git`
- 公开 fork：`https://github.com/gwenliu1025/transit-hub.git`
- 开发基线：官方 `origin/main@9ee10de`，包含正式标签 `v0.1.15@7ba0454`
- 开发分支：`codex/v0.1.15-production-fixes`
- 原工作区保持只读保留，不重置、不清理、不直接提交其中的混合改动。

## 合并策略

不把旧工作区整体合并到新版本。逐项解释旧改动的业务目的，在官方新版本中寻找对应数据流，使用测试先行方式重新实现。已被官方吸收或已不适用的旧改动不重复迁移。

首批必须保留的生产行为：

1. Sub2API 今日成本使用显式 `Asia/Shanghai` 日期区间，不使用受上游服务器日界线影响的 dashboard 汇总值。
2. 外层今日成本与净利润只统计 `lastSyncedAt` 属于目标北京时间日期的数据，排除失败站点跨日残留成本。
3. 当天处于 `syncing` 状态但已有当天有效指标的站点仍计入，避免同步期间数值闪烁。
4. 单个上游明细请求失败不遮蔽其他健康站点；鉴权刷新失败但现有访问凭证仍有效时不错误退出工作区。
5. 实时卡片和午夜快照使用同一日期过滤规则，上游余额不受日期过滤影响。

## 审计策略

审计与修复分离。本轮只修复已知生产问题；其余问题记录到中文审计报告，按 `P0`、`P1`、`P2`、`P3` 排序，并包含证据、影响、复现或触发条件、建议修复方向。审计覆盖：

- Go 单元测试、竞态检测、`go vet`、构建与数据库迁移；
- Vue/TypeScript 类型检查与生产构建；
- 身份认证、工作区隔离、外部请求、SSRF、凭证处理、附件与嵌入页面；
- 计费、余额、时区、缓存、定时任务、并发和失败降级；
- Docker、Compose、CI、版本号、标签和发布资产契约。

未经验证的猜测不列为 bug；无法稳定确认的事项单列为“待验证风险”。

## GitHub 发布策略

- 官方历史与官方标签不改写，所有官方 `v*` 标签原样同步到 fork。
- 自定义修复只提交到 `codex/v0.1.15-production-fixes`，验证完成后推送并创建中文草稿 PR，目标为 fork 的 `main`。
- 自定义版本不占用官方标签；后续发布使用独立标签，如 `v0.1.15-xiaoqian.1`。
- 不提交二进制、密钥、生产 `.env`、备份、数据库或会话数据。

## 验收标准

- 已知生产成本问题具备红绿回归测试；
- 后端全量测试、竞态测试、`go vet`、构建通过；
- 前端依赖锁定安装、类型检查和生产构建通过；
- Docker/Compose 配置验证通过；
- 审计报告列出所有已验证问题及待验证风险；
- fork 的官方标签与 upstream 一致；
- 推送内容不含敏感信息和临时构建产物。
